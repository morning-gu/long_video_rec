以下为完整研究文档，可直接保存为 Markdown。

# 文档 0：研究总纲

## 1. 研究问题

- **RQ1**：火山引擎/字节跳动、爱奇艺、Netflix、YouTube 各自最新的公开推荐系统采用了什么总体架构、建模方法与工程方案？
- **RQ2**：这些方案在目标函数、数据处理、召回/排序/重排、实时性、评估体系和新技术采用上有哪些共同趋势与实质差异？
- **RQ3**：从公开证据看，2024—2026 年推荐系统的主流演进方向是什么，四家厂商分别处于哪些不同阶段？

## 2. 核心结论

1. **没有单一“推荐算法”可以概括这些厂商。**  
   大型内容平台的推荐系统实际是多阶段系统，通常包含召回、粗排、精排、重排、实验平台、特征系统、实时训练、反馈回流等多个模块。

2. **四段式推荐漏斗仍是主流骨架。**  
   ```text
   多路召回 / Retrieval
      ↓
   粗排 / Pre-ranking
      ↓
   精排 / Multi-task Ranking
      ↓
   重排 / Re-ranking
      ↓
   A/B 实验 / 反馈回流
   ```

3. **2024—2026 年的主要变化不是推翻漏斗，而是改变每一层的内部形态。**  
   - 召回层从 embedding retrieval 走向 semantic ID、generative retrieval；
   - 排序层从手工特征 + 专用模型走向 sequence modeling、multi-task learning、foundation model、LLM ranker；
   - 目标从短期 CTR / engagement 扩展到长期满意度、留存、用户价值和平台生态；
   - 工程重点从离线批处理转向实时特征、在线训练、低延迟 serving 与系统-算法协同设计。

4. **四家厂商的公开证据强度差异很大。**
   - **Netflix**：公开叙事最完整，尤其 2024—2026 年 foundation model、generative recommender、LLM ranker 披露较多；
   - **YouTube / Google**：经典论文和 2025 年 Gemini / Semantic ID 方向证据较强；
   - **字节跳动 / 火山引擎**：工程系统、实时训练、Flink 特征链路、Monolith 论文证据较强，但完整业务链路公开有限；
   - **爱奇艺**：2020—2021 年有若干推荐工程公开分享，但 2024—2026 年推荐算法细节公开明显不足，横向比较不确定性最高。

## 3. 研究边界

本报告只讨论**公开可验证资料**，包括：

- 官方技术博客；
- 公司署名论文；
- arXiv 论文；
- 公开演讲；
- 官方文档；
- 可追溯的工程社区分享。

不使用无法核验的传闻，不将论文或博客等同于完整生产系统，不把招聘信息、二手解读当作生产架构证据。

# 文档 1：火山引擎 / 字节跳动 / 抖音推荐系统研究文档

## 1. 结论摘要

从公开证据看，字节跳动 / 抖音 / 火山引擎推荐系统的技术主线可以概括为：

> **多阶段推荐漏斗 + 实时数据链路 + 在线训练 + 大规模稀疏 embedding + 冷启动与粗排专项优化。**

与 Netflix、YouTube 相比，字节跳动公开披露的重点不在“完整的推荐算法体系”，而在：

1. 推荐系统的实时性；
2. 大规模 embedding 表的存储、更新和冲突处理；
3. 流式特征生产链路；
4. 在线训练与反馈闭环；
5. 冷启动、粗排等具体子问题。

因此，字节跳动公开证据中最具代表性的不是某个单点排序模型，而是 **Monolith** 及其背后的实时推荐系统实践。

---

## 2. 公开架构主线

根据公开论文与工程资料，抖音 / TikTok / 字节跳动推荐系统可以概括为：

```text
用户行为日志
   ↓
实时 / 离线特征生产
Kafka / BMQ / Flink / Spark / Hive / HDFS / Abase / RPC
   ↓
多路召回 Retrieval
   ↓
过滤 Filtering
   ↓
粗排 Pre-ranking
   ↓
精排 Ranking
   ↓
重排 / 混排 Re-ranking / Blending
   ↓
线上 A/B 实验
   ↓
反馈回流与模型更新
```

需要注意的是，这个架构图是根据不同公开材料拼合出的公开技术图景，不等于完整生产系统。

---

## 3. 关键技术模块

### 3.1 Monolith：实时推荐系统与 collisionless embeddings

字节跳动公开论文 **《Monolith: Real Time Recommendation System With Collisionless Embeddings》** 是其推荐系统公开资料中的关键证据。

论文的核心主题包括：

1. **Real-time recommendation**
   - 系统强调实时反馈和在线更新；
   - 用户行为变化可以较快进入模型训练链路。

2. **Collisionless embedding table**
   - 传统 embedding hashing 可能造成不同 ID 映射到同一个槽位，带来冲突；
   - Monolith 强调使用 collisionless embedding table，保证稀疏特征表示的唯一性和稳定性。

3. **Online training**
   - 不是单纯离线训练后定期上线；
   - 系统支持在线训练与滚动更新。

4. **大规模稀疏特征**
   - 推荐系统中的用户 ID、内容 ID、行为序列、上下文特征会形成超大规模稀疏 embedding；
   - Monolith 关注如何在大规模稀疏条件下高效训练和 serving。

5. **工程容错与可用性**
   - 在线训练要求系统具备故障恢复、训练一致性、服务稳定性等能力。

因此，Monolith 揭示的是字节跳动推荐系统在工程层的核心竞争力：

> **实时反馈 + 大规模稀疏建模 + 在线训练 + 低延迟服务。**

---

### 3.2 实时特征链路：Flink、Kafka、Spark、Abase

火山引擎开发者社区的《5 年迭代 5 次，抖音基于 Flink 的推荐系统演进历程》提供了较明确的特征工程证据。

该文提到的组件包括：

- **Kafka**
- **BMQ**
- **Hive**
- **HDFS**
- **Abase**
- **RPC**
- **Spark**
- **Flink**
- **Flink SQL**
- 有状态流式计算

这表明抖音推荐特征生产不是单纯的离线批处理，而是：

```text
日志采集
   ↓
流式 / 离线特征计算
   ↓
特征存储
   ↓
在线特征服务
   ↓
模型训练与推理
   ↓
反馈回流
```

其中，Flink 承担实时流式计算和状态维护，Spark / Hive / HDFS 承担离线批处理，Abase / RPC 等组件参与在线特征服务。

这与短视频场景高度相关：用户兴趣和内容热度变化快，系统必须让实时行为尽快进入模型。

---

### 3.3 冷启动：Next-User Retrieval

2025 年论文 **《Next-User Retrieval: Enhancing Cold-Start Recommendations via Large Language Models》** 直接指向 Douyin 推荐系统的冷启动问题。

公开摘要显示，该方案的核心思想是：

- 受 lookalike algorithms 启发；
- 通过 generative next-user modeling 缓解冷启动；
- 面向新用户或新内容等行为稀疏场景；
- 论文包含 offline experiments 和 online A/B tests。

这说明字节跳动 / 抖音在冷启动方向上已经公开探索：

> **用生成式建模和相似用户扩展，缓解新用户 / 新内容信号不足的问题。**

但该论文属于局部模块研究，不能说明整个抖音推荐系统已经全面转向 LLM 推荐架构。

---

### 3.4 粗排：Pre-ranking 与候选异质性

公开研究还出现针对推荐系统 pre-ranking 的讨论，核心问题是：

- 大规模推荐系统通常包含 retrieval、pre-ranking、ranking、re-ranking；
- 粗排需要从大量召回候选中快速筛选；
- 候选来源不同，分布可能高度异质；
- 如果用一个统一粗排模型处理所有候选，可能低估或高估某些来源的候选。

公开证据显示，粗排正在从简单轻量模型演化为：

- 与精排目标更一致；
- 候选分布感知；
- 支持更大候选规模；
- 兼顾延迟和效果。

这符合工业推荐系统的一般趋势：**粗排越来越像“压缩版精排”**。

---

## 4. 字节跳动推荐系统技术演进判断

### 阶段 1：离线特征 + 批量训练

早期推荐系统通常依赖：

- 离线日志；
- 批量样本拼接；
- 离线训练；
- 定期发布模型。

### 阶段 2：实时特征 + 流式计算

随着短视频反馈周期缩短，系统开始强调：

- Kafka / Flink 流式处理；
- 实时特征更新；
- 用户短期兴趣快速捕捉。

### 阶段 3：在线训练与实时更新

Monolith 的公开意义在于：

- 在线训练成为核心工程能力；
- embedding 表可以动态更新；
- 模型能更快响应用户兴趣和内容热度变化。

### 阶段 4：冷启动与生成式建模

2025 年 Next-User Retrieval 表明：

- 生成式建模开始进入冷启动子问题；
- LLM 或 generative modeling 被用于扩展用户 / 内容表征；
- 但公开证据尚未证明整个推荐主链路已经 LLM 化。

## 6. 关键局限

1. **公开资料远小于真实系统。**  
   抖音 / TikTok 的生产推荐系统规模极大，公开论文只披露局部模块。

2. **不同证据层次不能直接拼接。**  
   Monolith 是训练与 embedding 系统，Flink 文章是特征链路，Next-User Retrieval 是冷启动研究，它们不能简单等同于同一个完整生产架构。

3. **LLM 推荐证据不足。**  
   招聘信息或媒体报道中出现“推荐大模型”“多模态大模型”等表述，但不能作为生产系统架构的证据。

4. **长期价值与实验平台细节公开不足。**  
   虽然有 A/B test 证据，但完整实验平台、长期价值建模、用户留存优化方案尚未系统公开。

## 7. 火山引擎 / 字节跳动研究结论

从公开证据看，火山引擎 / 字节跳动推荐系统的核心竞争力是：

> **实时化、系统化、在线学习和大规模稀疏特征处理。**

其技术路线可概括为：

```text
实时行为流
  → 实时特征
  → 在线训练
  → 大规模稀疏 embedding
  → 多阶段推荐漏斗
  → A/B 实验反馈
```

它和 Netflix、YouTube 的差异在于：

- Netflix 公开重点更偏 foundation model、长期满意度、LLM ranker；
- YouTube 公开重点更偏大规模排序、Semantic ID、Gemini 适配；
- 字节跳动公开重点更偏实时工程系统、在线训练和特征链路。

# 文档 2：爱奇艺推荐系统研究文档

## 1. 结论摘要

爱奇艺推荐系统的公开披露有一个明显特点：

> **技术公开高峰集中在 2017—2023 年，尤其是 2020—2021 年的短视频推荐链路；2024—2026 年推荐系统内部算法的系统性公开明显减少。**

因此，对爱奇艺的研究必须区分：

- **可确认的公开方案**；
- **公开证据不足的方向**；
- **不能因为公开少就推断厂商没有做**。

从可核验资料看，爱奇艺推荐系统公开架构的主线是：

```text
多路召回 / 多兴趣召回
   ↓
粗排
   ↓
精排
   ↓
多目标融合
   ↓
在线推荐
```

其公开技术关键词包括：

- 召回 + 排序；
- 多兴趣召回；
- 粗排模型优化；
- MMoE；
- 多目标排序；
- Pareto 多目标优化；
- PSO 参数搜索；
- 双 DNN 在线知识蒸馏；
- 通用排序框架。

---

## 2. 公开架构主线

爱奇艺早期官方资料已经说明，其推荐系统主要分为两个阶段：

1. **召回**
   - 从千万级视频库中筛出几百到几千候选；
2. **排序**
   - 对候选内容进行更精细的偏好打分。

后续公开资料显示，架构逐步演进为：

```text
用户行为 / 视频特征
   ↓
多路召回
   ↓
多兴趣召回
   ↓
粗排
   ↓
精排
   ↓
多目标融合
   ↓
展示
```

与短视频平台相比，爱奇艺主站业务具有明显的长视频特征：

- 内容生命周期更长；
- 用户决策成本更高；
- 观看周期更长；
- 会员、广告、内容运营目标更复杂；
- 单条内容的消费时间远长于短视频。

不过，爱奇艺最详细的推荐技术公开主要来自短视频推荐链路，而非主站长视频推荐，因此需要谨慎迁移。

---

## 3. 关键技术模块

### 3.1 多兴趣召回

爱奇艺公开材料讨论过短视频推荐中的多兴趣召回技术。

其核心思想是：

- 用户兴趣不是单一的；
- 一个用户可能同时喜欢综艺、悬疑剧、喜剧、纪录片等；
- 单一用户向量容易把多个兴趣压缩成一个平均表示；
- 多兴趣召回将用户兴趣拆成多个向量或兴趣簇；
- 每个兴趣簇对应一条召回通路；
- 最终再合并候选。

这与工业推荐系统的多兴趣建模方向一致。

---

### 3.2 粗排

爱奇艺公开分享过短视频推荐粗排模型优化历程。

粗排的目标包括：

- 统一处理多路召回结果；
- 对候选进行初步打分；
- 降低精排计算压力；
- 提升召回和精排之间的目标一致性。

这说明爱奇艺公开链路中已经存在：

```text
召回 → 粗排 → 精排
```

的工业推荐范式。

---

### 3.3 多目标排序

爱奇艺在 InfoQ 等技术社区公开过短视频推荐中的多目标排序实践。

公开提到的技术包括：

1. **MMoE**
   - Multi-gate Mixture-of-Experts；
   - 多个 expert 网络共享底层表征；
   - 不同任务通过不同 gate 组合专家输出。

2. **多目标融合**
   - 对完播、互动、点击、播放时长等目标分别建模；
   - 再通过融合公式或策略生成最终排序分数。

3. **Pareto 多目标优化**
   - 在多个目标之间寻找更优平衡；
   - 避免单一目标提升导致其他目标下降。

4. **PSO 参数搜索**
   - 用粒子群算法搜索目标融合参数；
   - 降低人工调参成本。

公开材料中提到过业务收益，如人均播放时长、互动率提升。但由于缺少完整实验设置、置信区间和复现条件，这类数字应视为业务效果描述，而不是可独立复现的学术结论。

---

### 3.4 通用排序框架

爱奇艺公开过《通用排序框架在爱奇艺推荐的应用》。

其工程意义包括：

- 支持不同业务接入；
- 统一特征、样本、训练和 serving 链路；
- 降低新场景模型开发成本；
- 从单场景定制模型走向平台化排序能力。

这说明爱奇艺的推荐系统不仅在优化单点模型，也在建设更通用的排序基础设施。

---

### 3.5 双 DNN 与在线知识蒸馏

公开材料还提到过双 DNN 排序模型与在线知识蒸馏。

其目标通常包括：

- 在线或准在线更新；
- 用 teacher model 指导 student model；
- 降低复杂模型 serving 成本；
- 保持线上效果和推理效率之间的平衡。

但公开细节有限，无法判断其具体生产覆盖范围。

---

## 4. 2024—2026 年的最新公开状态

目前没有找到爱奇艺 2024—2026 年系统性公开的推荐算法论文或完整技术博客。

公开重心更多转向：

- AI 内容生产；
- 剧本评估；
- 虚拟拍摄；
- 微短剧；
- 长短内容融合；
- 广告与商业化生态。

因此，对“爱奇艺最新推荐算法”的准确回答是：

> **公开证据不足以还原其 2024—2026 年完整推荐系统方案。可确认的公开演进仍主要停留在 2020—2023 年的多兴趣召回、粗排、多目标精排和通用排序框架方向。**

---

## 6. 爱奇艺推荐系统的本质特征

从公开证据看，爱奇艺推荐系统呈现的是一种更传统的工业推荐演进路径：

```text

  → 机器学习排序
  → 深度学习排序
  → 多路召回
  → 多目标精排
  → 通用排序框架
```

与 Netflix、YouTube、字节跳动相比，爱奇艺公开证据中的特征是：

1. **业务目标更偏长视频消费与会员价值**；
2. **推荐链路更强调多目标平衡**；
3. **工程公开重点在排序框架和多目标建模**；
4. **2024—2026 年推荐算法公开明显减少，无法判断其内部是否已经采用 foundation model 或 LLM ranker。**

爱奇艺公开可确认的推荐方案是：

> **多路召回 / 多兴趣召回 + 粗排 + 多目标精排 + 通用排序框架。**

但由于 2024—2026 年推荐系统细节公开不足，不能负责任地宣称爱奇艺已经采用与 Netflix、YouTube 类似的 foundation model 或 generative recommendation 主链路。

# 文档 3：Netflix 推荐系统研究文档

## 1. 结论摘要

Netflix 是四家厂商中 2024—2026 年推荐系统公开叙事最完整的公司之一。

其最新公开技术演进可以概括为：

> **从大量专用推荐模型，走向统一的个性化 foundation model、大规模 sequence modeling、generative recommender、LLM-backed ranker 和长期满意度优化。**

Netflix 的公开技术路线不是简单地把 GPT 类通用大模型接到推荐系统上，而是分成了几条相互关联的路线：

1. **个性化 foundation model**
   - 学习会员长期交互历史；
   - 学习内容侧深层表示；
   - 服务多个下游推荐应用。

2. **大规模 sequence modeling**
   - 将用户行为 token 化；
   - 用 transformer 类结构建模长期行为序列；
   - 使用 sparse attention、sliding window sampling、KV caching 处理长历史与低延迟冲突。

3. **层级多任务学习**
   - FM-Intent 先预测用户 session intent；
   - 再用 intent 辅助 next-item prediction。

4. **长期满意度与 reward engineering**
   - 将推荐视为 contextual bandit 问题；
   - 通过 proxy reward 和 delayed feedback prediction 对齐长期会员价值。

5. **生成式推荐**
   - 将推荐建模为 next-event prediction；
   - 扩展到约 O(1B) 参数量级；
   - 探索推荐系统自己的 scaling law。

6. **LLM-backed ranker**
   - GenRec 将内部 foundation LLM 适配为推荐排序器；
   - 引入 context engineering、catalog-aware scoring、reward alignment 和低延迟推理策略。

---

## 2. 总体架构演进

Netflix 的公开架构可以概括为：

### 阶段 1：多个专用模型

传统 Netflix 推荐系统由多个专用模型组成，例如：

- Continue Watching；
- Today’s Top Picks for You；
- 个性化榜单；
- 搜索与推荐联动；
- artwork personalization。

这种模式的问题包括：

- 模型维护成本高；
- 创新难以跨场景复用；
- 特征和样本体系分散；
- 不同模型对同一用户的理解不一致。

### 阶段 2：Foundation Model for Personalized Recommendation

2025 年，Netflix 公开其个性化推荐 foundation model。

核心思想是：

- 用一个模型学习会员长期交互历史；
- 学习内容侧表示；
- 通过 embeddings、fine-tuning、shared weights 支持下游任务；
- 将原本分散的 preference learning 集中化。

这可以理解为推荐系统的“中枢表征层”。

### 阶段 3：应用集成

2025—2026 年公开资料显示，Netflix 将 foundation model 集成到多个个性化应用中，包括：

- homepage；
- search；
- recommendation；
- artwork personalization。

公开材料提到过不同的集成方式：

- 直接使用模型输出；
- 使用 user / entity embeddings；
- 复用模型子图；
- 对下游任务 fine-tuning。

2026 年公开资料还显示，foundation model 可能采用周期性预训练与更高频微调结合的方式，例如：

- 每月从大规模数据预训练；
- 之后基于较新数据进行日常或周期性 fine-tuning。

这说明 Netflix 的 foundation model 不是一次性静态模型，而是持续更新的生产系统。

---

## 3. 关键技术模块

### 3.1 Interaction tokenization：用户行为 token 化

Netflix 将用户交互历史转换为序列 token，需要处理：

- 什么算一次有意义交互；
- 多次交互是否合并；
- 同一 title 的重复行为如何表示；
- 观看时长如何编码；
- 设备、时间、地点、上下文如何进入 token；
- 过长历史如何截断或采样。

这使推荐问题从传统排序问题变成：

> **用户行为序列上的 next-event prediction。**

---

### 3.2 Request-time features 与 post-action features

Netflix 将特征分为两类：

1. **Request-time features**
   - 请求发生时已经可用；
   - 例如设备、时间、地点、surface、登录上下文。

2. **Post-action features**
   - 用户行为发生后才可用；
   - 例如实际观看的 title、观看时长、互动结果、内容 metadata。

在 next-item prediction 中，Netflix 会将：

- 当前 step 的 request-time features；
- 上一个 step 的 post-action features；

结合起来预测下一步交互。

这个设计的意义是：

> **上下文信息和历史行为信息共同进入同一个序列建模框架。**

---

### 3.3 Sparse attention、sliding window sampling、KV caching

Netflix 公开资料强调，foundation model 必须同时处理：

- 超长用户历史；
- 毫秒级线上延迟；
- 大规模 serving 请求。

为此，公开方案包括：

1. **Sparse attention**
   - 降低 self-attention 计算成本；
   - 扩展可用上下文窗口。

2. **Sliding window sampling**
   - 训练时从完整历史中采样重叠窗口；
   - 让模型在不同 epoch 看到不同历史片段。

3. **KV caching**
   - 推理时复用历史上下文计算；
   - 降低多步或重复推理成本。

这说明 Netflix 的 foundation model 不是单纯离线研究模型，而是面向线上低延迟推荐场景设计的。

---

### 3.4 FM-Intent：层级多任务学习

2025 年 Netflix 公开 **FM-Intent: Predicting User Session Intent with Hierarchical Multi-Task Learning**。

其核心思想是：

- 用户在一个 session 中有潜在 intent；
- 只预测 next item 可能不够；
- 可以先预测 intent；
- 再让 intent 辅助 next-item prediction。

这形成层级结构：

```text
长期用户历史
   ↓
预测 session intent
   ↓
intent-aware next-item prediction
   ↓
下游推荐应用
```

公开材料提到，FM-Intent 在 Netflix user engagement dataset 上取得了离线提升，但需要注意：

- 这是离线实验结果；
- 数据集是 sampled dataset；
- 不能直接等同于线上业务指标。

---

### 3.5 长期会员满意度：contextual bandit 与 reward engineering

Netflix 2024 年公开《Recommending for Long-Term Member Satisfaction at Netflix》。

核心观点是：

- 只优化点击、播放、短期 engagement 可能无法代表长期满意度；
- 推荐系统应优化长期会员价值；
- Netflix 将推荐建模为 contextual bandit 问题；
- 通过 reward engineering 设计 proxy reward；
- 处理 delayed feedback 和 missing feedback。

这意味着 Netflix 的目标函数正在从：

```text
短期互动最大化
```

转向：

```text
长期会员满意度 / 长期 utility 最大化
```

其关键挑战包括：

- 长期反馈延迟；
- 反馈稀疏；
- reward 不可直接观测；
- 在线实验周期长；
- 短期指标与长期目标可能冲突。

---

### 3.6 大规模生成式推荐

Netflix 2026 年公开《Towards Generalizable and Efficient Large-Scale Generative Recommenders》。

公开要点包括：

- 将推荐建模为行为序列上的生成任务；
- 模型从约 O(1M) 扩展到 O(1B) 参数；
- 使用大规模周期性训练数据；
- 关注 efficiency、cold start、multi-token alignment、serving distribution shift 等问题；
- 探索推荐系统自身的 scaling law。

这表明 Netflix 正在尝试建立推荐领域自己的大规模训练体系，而不是简单复用通用 LLM 的训练范式。

---

### 3.7 GenRec：LLM-backed recommendation ranker

Netflix 2026 年公开 **GenRec: Towards LLM-Native Recommendation at Netflix**。

公开叙事显示，GenRec 的路线包括：

1. **内部 foundation LLM 适配**
   - 不是直接调用通用外部 LLM；
   - 而是在 Netflix 数据和推荐场景上适配模型。

2. **Context engineering**
   - 将用户上下文、设备、surface、locale、时间等信息表达为 LLM 可理解的形式。

3. **Catalog-aware scoring**
   - LLM 不自由生成任意片名；
   - 输出受到 catalog 约束，避免幻觉。

4. **Reward alignment**
   - 使用 reward signal 对齐长期满意度和业务目标。

5. **低延迟推理**
   - 公开讨论过 prefill-only 等推理策略；
   - 目标是在大规模线上服务中控制成本和延迟。

GenRec 的意义在于：

> **Netflix 正在把 LLM 从内容理解工具，推进为推荐排序模型本身。**

但需要注意，公开资料显示的是有限 A/B 或实验进展，不代表整个 Netflix 推荐系统已经完全被 LLM ranker 替代。

---

### 3.8 Artwork personalization 与 LLM post-training

Netflix 还公开过 artwork personalization 相关的 LLM post-training 研究。

其目标是：

- 根据用户偏好选择不同封面、宣传图；
- 让素材更符合用户兴趣；
- 用 LLM 后训练学习用户与视觉素材之间的关系。

公开结果显示，LLM post-training 在 held-out 实验中优于现有 production model，但这类结果仍需区分：

- offline held-out evaluation；
- online A/B test；
- 长期业务影响。

# 文档 4：YouTube / Google 推荐系统研究文档

## 1. 结论摘要

YouTube / Google 推荐系统的公开主线是：

> **大规模多阶段推荐漏斗 + embedding retrieval + multi-task ranking + sequence modeling，正在向 Semantic ID、Gemini / LLM、generative retrieval 和语义理解方向演进。**

与 Netflix 相比，YouTube 公开披露的重点更偏：

- 超大规模候选生成；
- 多任务排序；
- 视频语义 token 化；
- Semantic ID；
- Gemini 适配；
- 生成式检索。

与字节跳动相比，YouTube 公开的工程系统细节较少，但其经典论文和 Google 研究生态使得其算法架构证据非常清晰。

---

## 2. 公开架构主线

YouTube 最经典的公开架构来自 2016 年论文：

**《Deep Neural Networks for YouTube Recommendations》**

其核心架构是：

```text
用户历史行为 / 上下文
   ↓
Candidate Generation
大规模候选生成
   ↓
Ranking
候选排序
   ↓
展示
```

其中：

- Candidate Generation 将海量视频缩小到较小候选集；
- Ranking 对候选视频进行精细排序；
- 用户历史行为被映射为 embedding；
- embedding 相似度用于召回。

2019 年论文：

**《Recommending What Video to Watch Next: A Multitask Ranking System》**

进一步公开了 watch-next 场景中的 multi-objective ranking 设计。

这说明 YouTube 的公开架构长期保持：

> **候选生成 + 精细排序** 的主线。

---

## 3. 关键技术模块

### 3.1 Candidate Generation / Retrieval

YouTube 2016 年论文明确了 candidate generation 的重要性：

- 视频库规模极大；
- 无法对所有视频做完整精排；
- 需要先用高效方法召回候选。

公开技术路线包括：

- 用户 embedding；
- 视频 embedding；
- 近似最近邻检索；
- 多路候选生成；
- 历史行为序列表示。

这与工业界 two-tower retrieval 思路一致：

```text
user / query tower
        ↓
user embedding
                → ANN retrieval
item tower
        ↓
item embedding
```

two-tower 的优势是：

- item embedding 可以离线构建；
- 线上只计算 user tower；
- 支持大规模低延迟召回。

---

### 3.2 Multi-objective ranking

2019 年 YouTube 论文公开了大规模 multi-objective ranking 系统。

其核心问题是：

推荐下一视频不能只优化一个指标，而需要同时考虑：

- 是否观看；
- 观看时长；
- 满意度；
- 互动行为；
- 后续行为；
- 平台生态目标。

因此，ranking 层需要：

- 多任务学习；
- 多目标融合；
- 偏差处理；
- 不同任务之间的冲突处理。

这也是现代视频推荐系统的共同趋势：

> **从 CTR 模型走向 multi-objective / multi-task ranking。**

---

### 3.3 Sequence modeling

YouTube 2016 年论文已经使用用户历史观看行为作为核心特征。

后续工业推荐系统普遍将 sequence modeling 引入：

- 短期兴趣；
- 长期兴趣；
- session 内兴趣转移；
- 跨场景行为；
- 负反馈；
- 时间衰减。

虽然 YouTube 对最新 sequence model 细节公开有限，但其技术主线与 Google 推荐研究生态一致：

```text
用户行为序列
   ↓
embedding / attention / transformer
   ↓
用户兴趣表示
   ↓
召回与排序
```

---

### 3.4 Semantic ID 与 generative retrieval

Google 的推荐系统研究在 2023 年后明显转向 semantic ID 和 generative retrieval。

代表工作是：

**《Recommender Systems with Generative Retrieval》**

其核心思想是：

- 为 item 学习 semantic ID；
- 将推荐任务转化为生成 semantic ID 的任务；
- 模型不再只是通过向量相似度检索 item；
- 而是可以直接生成候选 item 的 token 序列。

这带来一个重要变化：

```text
传统召回：
user embedding → ANN → item embedding

生成式召回：
user history / context → generate semantic ID → candidate item
```

这类方法的意义在于：

- item 可以被结构化 token 表示；
- 检索过程可以与序列生成统一；
- LLM 或 transformer 可以更自然地建模推荐任务。

---

### 3.5 Gemini / Large Recommender Model

2025 年公开演讲：

**“Teaching Gemini to Speak YouTube: Adapting LLMs for Video Recommendations to 2B+ DAU”**

披露了 YouTube 将 Gemini 适配为视频推荐模型的方向。

公开叙事中的关键词包括：

- **Large Recommender Model / LRM**
- **Gemini checkpoint adaptation**
- **Semantic ID**
- **视频 token 化**
- **generative video retrieval**
- **大规模低延迟 serving**

其技术方向可以概括为：

```text
视频内容
   ↓
Semantic ID / video tokenization
   ↓
Gemini-based Large Recommender Model
   ↓
生成式候选检索 / 排序
   ↓
现有推荐漏斗集成
```

需要注意的是：

- 该证据主要来自公开演讲；
- 不是完整系统论文；
- 不能证明 YouTube 已经完全用 LRM 替换现有推荐系统。

更合理的判断是：

> **YouTube 正在把 Gemini / Semantic ID / generative retrieval 叠加到既有大规模推荐漏斗中，而不是完全推翻传统 retrieval-ranking 架构。**

## 6. YouTube 的核心差异

YouTube 与其他厂商相比，差异化在于：

1. **内容形态复杂**
   - 长视频、短视频、直播、搜索、推荐、订阅、频道关系交织。

2. **搜索与推荐高度耦合**
   - 用户主动搜索和历史观看共同影响推荐。

3. **超大规模候选空间**
   - 需要极强的 retrieval 和 ANN 能力。

4. **多目标排序成熟**
   - 2019 年已经公开大规模 multi-objective ranking 系统。

5. **Semantic ID / Gemini 方向明确**

YouTube 的推荐系统主线是：

> **大规模多阶段漏斗 + embedding retrieval + multi-objective ranking + sequence modeling，正在引入 Semantic ID、Gemini / LLM 和 generative retrieval。**

最重要的公开变化是：

> **从“专用 embedding + 排序模型”，走向“语义 token + 大模型适配 + 生成式检索与排序”。**

但这不意味着传统 two-tower、multi-task ranking 被完全替代，更合理的判断是：

> **LLM / generative recommendation 正在被叠加进既有系统，成为新的召回、语义理解和排序能力。**

## 3. 技术趋势对比

### 趋势 1：多阶段漏斗仍是主流

四家厂商公开证据都支持推荐系统不是单一模型，而是多阶段系统。

主流结构为：

```text
召回
  → 粗排
  → 精排
  → 重排
```

不同厂商对阶段的命名和披露粒度不同：

- 字节跳动公开材料更强调 retrieval、pre-ranking、ranking、re-ranking；
- 爱奇艺公开材料强调召回、粗排、精排；
- YouTube 经典论文强调 candidate generation 和 ranking；
- Netflix 近期更强调 foundation model 与下游任务，而不是传统漏斗的每一层。

因此，趋势不是“漏斗消失”，而是：

> **漏斗仍存在，但每层之间的表征、目标和训练样本正在更深度共享。**

---

### 趋势 2：排序从单目标走向 multi-objective / long-term value

早期推荐系统常以 CTR 为核心目标。现在公开方案普遍转向：

- 观看概率；
- 观看时长；
- 完播；
- 互动；
- 满意度；
- 留存；
- 长期会员价值；
- 创作者生态；
- 内容安全与公平性。

代表性证据：

- YouTube 2019 年 multi-objective ranking；
- 爱奇艺 MMoE、Pareto、PSO 多目标融合；
- Netflix 长期满意度和 reward engineering；
- 字节跳动实时行为预估和多目标方向，虽然公开细节较少。

---

### 趋势 3：sequence modeling 成为核心底座

用户历史行为不再只是若干离散特征，而是被组织成序列。

公开证据最强的是 Netflix：

- interaction tokenization；
- transformer；
- sparse attention；
- sliding window sampling；
- KV caching。

YouTube 也长期使用用户历史观看行为，但最新 sequence model 细节公开较少。

爱奇艺在该方向公开不足。

字节跳动有实时行为系统，但完整 sequence model 架构公开有限。

---

### 趋势 4：Foundation model 化

Netflix 是该方向公开最明确的公司：

- 一个 foundation model 服务多个个性化任务；
- 下游通过 embeddings、fine-tuning、shared weights 复用；
- homepage、search、recommendation、artwork personalization 共享用户与内容理解。

YouTube 的对应方向是：

- Gemini-based Large Recommender Model；
- Semantic ID；
- 视频语义 token 化；
- generative retrieval。

字节跳动和爱奇艺目前没有同等强度的公开证据。

---

### 趋势 5：Semantic ID 与 generative retrieval 兴起

Google / YouTube 方向最明确：

- item 被表示为 semantic ID；
- 推荐可以变成生成 semantic ID 的任务；
- 与传统 ANN retrieval 形成互补。

Netflix 则将其扩展为 generative recommender：

- 用户行为序列上的 next-event prediction；
- 从 O(1M) 到 O(1B) 参数规模；
- 探索推荐系统自己的 scaling law。

这说明推荐系统正在出现一个新的范式：

> **从“向量检索 + 排序”走向“语义 token + 生成式检索 + 排序”。**

---

### 趋势 6：实时化与在线学习仍是短视频系统的关键优势

字节跳动公开证据中最突出的是：

- Kafka / Flink 流式特征；
- Monolith online training；
- collisionless embedding table；
- 实时反馈闭环。

这与短视频场景高度匹配：

- 用户兴趣变化快；
- 内容生命周期短；
- 新内容冷启动压力大；
- 实时反馈信号密集。

相比之下：

- Netflix 更强调周期性预训练与持续微调；
- YouTube 公开资料更偏算法和大规模检索；
- 爱奇艺公开证据不足。

---

### 趋势 7：LLM 进入推荐系统，但不是简单调用通用 LLM

Netflix GenRec 和 YouTube Gemini 方向都表明，LLM 化推荐的关键不是直接问 LLM“推荐什么”，而是解决：

- catalog 约束；
- 推理延迟；
- 用户长期行为序列压缩；
- reward alignment；
- context engineering；
- 语义 token 表示；
- 与现有系统融合。

因此，更准确的技术路线是：

```text
通用 LLM / foundation model
   ↓
领域适配
   ↓
推荐数据后训练
   ↓
catalog-aware 输出
   ↓
低延迟 serving
   ↓
与既有推荐漏斗融合
```

4. sequence modeling 越来越重要；
5. semantic ID / generative retrieval 开始进入主流；
6. LLM 被用于推荐排序和语义理解，但需解决延迟、catalog 约束和 reward alignment；
7. 系统与算法协同设计成为关键。

**实质差异：**

1. **字节跳动偏实时工程**
   - 在线训练、实时特征、大规模稀疏 embedding 是公开证据最强的部分。

2. **爱奇艺偏传统工业推荐演进**
   - 公开证据集中在多目标排序、粗排和通用排序框架，最新细节不足。

3. **Netflix 偏 foundation model 与长期满意度**
   - 从模型整合走向个性化基础模型，并进一步探索 LLM-native recommendation。

4. **YouTube 偏超大规模检索、多任务排序与 Semantic ID**
   - 传统漏斗成熟，同时向 Gemini / generative retrieval 演进。

### RQ3：2024—2026 年主流演进方向是什么？

主流方向可以概括为六个词：

```text
实时化
序列化
多目标
长期价值
语义 token
生成式推荐
```

更具体地说：

1. **实时化**
   - 实时特征、实时反馈、在线训练。

2. **序列化**
   - 用户历史从离散特征变成行为序列。

3. **多目标**
   - 点击、时长、完播、满意度、留存、生态目标共同优化。

4. **长期价值**
   - 从短期 engagement 转向长期满意度、长期 utility 和用户生命周期价值。

5. **语义 token**
   - item 不再只有 ID embedding，而是被表示为 semantic ID 或行为 token。

6. **生成式推荐**
   - 召回和排序开始引入 generative retrieval、LLM ranker、foundation model。

---

## 7. 总判断

如果要用一句话概括四家厂商的最新方案：

> **推荐系统正在从“多路召回 + 特征工程 + 多任务精排”的传统工业范式，演进为“实时数据闭环 + 长序列建模 + foundation model + 多目标长期价值优化 + Semantic ID / generative recommendation”的新范式。**

但四家厂商所处阶段不同：

- **字节跳动**：实时化与在线学习体系证据最强；
- **爱奇艺**：传统多目标推荐证据较清楚，但最新公开断层明显；
- **Netflix**：foundation model 与 LLM-native recommendation 公开推进最深；
- **YouTube / Google**：超大规模检索、排序与 Semantic ID / Gemini 化方向最明确。

最终，生成式推荐并不是完全替代传统推荐漏斗，而是与漏斗融合：

```text
传统推荐系统
  + 实时特征与在线学习
  + 长序列建模
  + foundation model
  + Semantic ID
  + LLM ranker
  + 长期价值 reward
= 下一代推荐系统
```
