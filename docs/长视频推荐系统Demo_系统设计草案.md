# 长视频推荐系统 Demo — 系统设计草案

> 依据 `research/` 下研究洞察文档（01 趋势洞察、02 阶段算法、03 业界架构、04 算法矩阵、算法总结/数据集系列）起草。
> 用途：**竞赛/评审演示**。目标：快速构建一条可讲解、可演示、有评测数据支撑的端到端长视频推荐链路。
> 决策状态：O1（实时回流立即生效）/ O2（LLM 预算无上限）/ O3（消融对比默认开启）已于 2026-09-17 确认，无剩余开放问题（§11）。

---

## 1. 目标、假设与范围

### 1.1 设计目标

演示工业界四段式推荐漏斗（召回 → 粗排 → 精排 → 重排）+ 上下文决策 + LLM 增强层的完整协作，并以 Netflix 风格 Web 界面呈现，用离线评测数据证明个性化效果。

研究文档的核心结论支撑这一架构选择：

- 四家厂商（字节/爱奇艺/Netflix/YouTube）公开证据共同支持"多路召回 → 粗排 → 精排 → 重排"漏斗仍是主流骨架（文档 03 §2、文档 04 §6）；
- 基础系统推荐组合：ItemCF + 热门 + 双塔召回 / FM 或轻量 DNN 粗排 / Wide&Deep·DeepFM 精排 / 规则去重 + 类型打散重排（文档 02 §6）；
- LLM 定位是"语义理解、重排、解释，与传统链路互补而非替代"（文档 01 §7 趋势二、文档 03 趋势 7）——Demo 采用 LLM 重排 + 推荐理由生成的低风险形态。

### 1.2 显式假设

| # | 假设 |
|---|---|
| A1 | 数据：MovieLens-1M（6040 用户 × ~3700 电影 × 100 万评分），评分 ≥4 视为隐式正反馈；通过 `links.csv` 关联 TMDB 获取元数据与海报（文档 02_06 §9 推荐组合） |
| A2 | 单机 CPU 环境，全部离线训练分钟级完成，无分布式/流式/在线训练（模型参数不做在线更新，见 D8） |
| A3 | LLM API 可用且**预算无上限**（O2）：作用于最终 Top-20 候选（重排 + 理由）与自然语言查询；缓存仅用于延迟优化；不进实时主链路，LLM 不可用时系统完整可用（降级） |
| A4 | 时延目标：主链路单请求 < 500ms（含在线前向计算用户向量）；LLM 路径 1–3s 可接受（缓存命中则同主链路） |
| A5 | 电影粒度建模（非 episode/season 粒度）——ML-1M 无剧集结构，episode-level 建模列为扩展方向（文档 01 §4.2） |

### 1.3 非目标（明确排除，且需在演示话术中如实说明）

研究文档指出的以下工业能力，公开数据或 Demo 规模无法支撑，**不纳入本期**：

- 实时特征链路（Kafka/Flink）与在线训练（Monolith 式）——字节路径（文档 03 文档 1）；Demo 用"在线前向 + 离线权重"做单机替身（§4.6）；
- 真实多行为标签（完播/弃剧/续看/时长）与多目标精排的**真实**训练——公开数据空白（文档 02_06 §10.2），只保留多目标框架接口；
- 家庭/共看、封面个性化（artwork personalization）、长期留存/流失建模（文档 01 §4.3–4.5）；
- A/B 实验平台与反事实评估。

## 2. 总体架构

```text
┌─────────────────────────── 离线管线（脚本，一次构建） ───────────────────────────┐
│  ML-1M 下载 + TMDB 元数据关联（元数据/海报URL/简介缓存）                          │
│   → ItemCF 相似度矩阵（预计算）                                                  │
│   → 双塔模型训练（user/item embedding + Faiss 索引）                             │
│   → SASRec-lite 序列模型训练                                                     │
│   → DeepFM-lite 精排模型训练                                                     │
│   → 离线评测报告（Recall@K / NDCG@K / HR@K + 多样性/覆盖率/流行度偏差）           │
└──────────────────────────────────────────────────────────────────────────────┘
                                        ↓ 产物落盘（模型/索引/SQLite/Parquet）
┌─────────────────────────── 在线服务（FastAPI 单进程） ──────────────────────────┐
│  请求（user_id + 上下文：时段/设备/最近行为）                                     │
│   → ⓪ 用户状态实时层（内存序列/画像/已看集合，写透 SQLite，O1）                    │
│   → ① 多路召回（并发）                                                          │
│       ItemCF │ 双塔+ANN │ SASRec 序列 │ 热门兜底 │ 继续观看                      │
│   → ② 配额融合去重（~500–800 候选）                                              │
│   → ③ 粗排：轻量双塔点积 + 先验校准（500 → 200）                                 │
│   → ④ 精排：DeepFM-lite 多特征排序（200 → Top-50）                              │
│   → ⑤ 重排：已看过滤/类型打散/同系列限频 + MMR 多样性 + 冷门保量（→ Top-20）      │
│   → ⑥ LLM 层（异步、缓存、可降级）：Top-20 重排 + 推荐理由生成                    │
│   → 响应：多行结构（为你推荐 / 因为看过X / 热门榜 / 冷门佳片…）                    │
└──────────────────────────────────────────────────────────────────────────────┘
              ↑ 实时回流（O1：点击/负反馈 → ⓪ 用户状态层，下一次请求即生效）
┌─────────────────────────── 演示前端（静态页） ─────────────────────────────────┐
│  Netflix 风格行式首页 │ TMDB 海报 │ 推荐理由气泡 │ 用户切换                       │
│  消融开关（O3，默认开启）：纯热门 vs 完整链路，支持同屏对比                        │
└──────────────────────────────────────────────────────────────────────────────┘
```

设计原则：**漏斗各阶段均为可插拔接口**——每个阶段都先有最简实现保底，后续独立升级替换，不推倒重来。这本身即是多阶段架构的演示点（文档 01 §6：分层的原因是工程约束下的效果/时延/成本权衡）。

## 3. 数据设计

| 数据 | 存储 | 说明 |
|---|---|---|
| 电影/用户元数据、TMDB 元数据、海报 URL | SQLite（`meta.db`） | ML-1M 规模 SQLite 足够；工业对应物为特征平台/Redis（演示话术注明） |
| 交互数据（评分→隐式反馈） | Parquet + 内存 DataFrame | 训练用；按时间戳排序构造序列 |
| 双塔 embedding、SASRec item embedding | Faiss 索引 + `.npy` | 双塔索引 `IndexFlatIP`（3700 部电影精确检索即可）；25M 规模才需 HNSW |
| 模型权重 | PyTorch `state_dict` | 双塔 / SASRec-lite / DeepFM-lite 共用 torch 单框架 |
| 演示事件回流（点击、忽略、负反馈） | 进程内存态 + 写透 SQLite `events` 表 | O1：内存态供在线前向即时读取（下次请求即生效），SQLite 供重启恢复（R7） |
| LLM 结果缓存 | SQLite `llm_cache`（key=请求指纹） | O2 后定位为延迟优化（命中 <50ms），不再承担成本控制 |

**标签构造**：评分 ≥4 = 正反馈；时间切分（每用户留最后一个正样本做测试，其余做训练）——避免随机切分的时间信息泄漏（文档 01 §5.2、Hidasi & Czapp 批评）。

**TMDB 依赖处理**：元数据与海报 URL 在离线阶段批量拉取并缓存本地；评审环境无外网时海报仍可展示（风险 R4）。

## 4. 漏斗各阶段设计

### 4.1 召回层（多路并发，配额融合）

| 通道 | 算法 | 每路配额 | 依据（研究文档） |
|---|---|---|---|
| ItemCF | 共现相似度（余弦 + 热门惩罚公式，文档 02_01 §1.1），取用户近期高分电影 Top-3 的相似片 | 200 | 经典稳定、可解释，适合电影共现关系强 |
| 双塔 + ANN | user tower（ID + 历史行为聚合 + 类型偏好）× item tower（ID + 类型 + 年代 + [可选]TMDB 文本语义向量），in-batch + 均匀负采样混合训练 | 300 | 工业主流召回（YouTube candidate generation 主线，文档 03 文档 4） |
| 序列召回 | SASRec-lite（最近 50 部观影序列 → next-item） | 150 | 捕捉兴趣演化/追剧迁移；选 SASRec 而非 BERT4Rec：自回归目标与线上 next-item 一致（文档 02_01 §4.3 指出 BERT4Rec 训练-推理目标偏差） |
| 热门兜底 | 全局热门 + 分类型热门（贝叶斯平均评分平滑） | 50 | 新用户冷启动与基础覆盖（文档 02_01 §9） |
| 继续观看 | 最近交互的系列/同 IP 延续 | 50 | 上下文决策的"观看进度"通道（文档 02 §5） |

**融合策略**：分层配额截断 + 去重（文档 02_01 §10.3）；各路分数仅在路内排序，跨路不做分数加权（避免量纲不一致问题，演示时更易讲解）。

### 4.2 粗排（轻量，架构位）

- 实现：复用双塔 embedding 点积 + 热度/新鲜度先验的轻量线性校准，500 → 200。
- **诚实定位**：ML-1M 候选仅数百，粗排的工业必要性（万级候选快速打分）在 Demo 规模下不成立；保留它是为了完整演示漏斗概念与"粗排=压缩版精排"的演进趋势（文档 03 文档 1 §3.4）。
- 备选：砍掉粗排直接精排——不推荐，评审演示中四段完整性更有讲解价值。

### 4.3 精排（效果核心）

- 模型：DeepFM-lite（FM 二阶交叉 + DNN 高阶），三类特征：
  - 用户侧：ID embedding、活跃度、类型偏好分布（观影历史 genre 直方图）；
  - 物品侧：ID embedding、类型、年代桶、热度分、TMDB popularity、[可选]语义向量；
  - 交叉/上下文：用户类型偏好 × 电影类型匹配度、时段、DIN 思想简化版（目标电影与用户近期电影 embedding 的相似度作为特征，体现"兴趣激活"）。
- 目标：**单目标**（正反馈概率）。多目标（MMoE/PLE）是工业标配（文档 02 §3），但 ML-1M 无完播/时长/弃剧标签，**不伪造多目标**——保留多头输出接口，演示话术如实说明这是公开数据空白（文档 02_06 §10.2）。
- 训练样本：召回日志不可得，用「正样本 + 全库/批次负采样」构造，负采样比例 1:4，曝光偏差缓解列为扩展（文档 01 §5.2）。

### 4.4 重排（列表级）

1. 规则层：已看过滤（含演示点击回流）、同类型连续 ≤2 部打散、同系列/同导演限频（文档 02 §4 常见约束）；
2. MMR 多样性：基于 item embedding 余弦距离，λ≈0.4（文档 02 §4：DPP/MMR）；
3. 冷门保量：Top-20 中非热门 ≥20%——多样性不是附加项而是业务需求（文档 01 §5.4），且是可直接展示的差异化指标。

### 4.5 LLM 增强层（异步、缓存、可降级）

| 能力 | 实现 | 对应研究趋势 |
|---|---|---|
| LLM Rerank | Top-20 候选 + 用户画像摘要 + 电影元数据 → 结构化 JSON 重排；**只允许从候选集中选择（catalog 约束，防幻觉）** | GenRec 的 catalog-aware scoring（文档 03 文档 3 §3.7）；LLM 零样本排序（文档 01 §3.4） |
| 推荐理由 | 为 Top-12 每部生成一句话理由（"因为你看过《盗梦空间》…"），按请求指纹缓存 | LLM 提供解释能力，传统模型负责行为信号（文档 01 §7 趋势二） |
| 自然语言查询（M5） | "来部轻松的科幻片" → LLM 解析为结构化偏好 → 类型过滤 + 双塔语义检索 | 自然语言偏好交互（文档 02_01 §8.4）；O2 后不受预算约束 |

工程约束（O2 预算无上限后的定位）：缓存仅用于延迟优化；超时 3s 降级为精排结果；并发限制放宽至 4（防请求风暴，非预算约束）；**主链路零依赖**（评审现场 LLM 不可用不影响演示）——预算放开改变的是调用范围，不改变可用性设计。

### 4.6 上下文决策与实时回流（O1：点击后下一次请求即变化）

- 时段/星期特征进精排；"继续观看"独立召回通道；设备/家庭上下文不做（A2/非目标）。
- **实时回流机制**（"实时化"趋势的单机替身，文档 03 趋势 6）：
  1. **用户状态实时层**：进程内维护每用户的交互序列、类型偏好直方图、已看/抑制集合；点击/负反馈经 `/api/event` 即时更新内存态并写透 SQLite，重启时从 `events` 表重建；
  2. **在线前向、离线权重**：双塔 user embedding 与 SASRec 序列编码在每次请求时**在线前向计算**（ML-1M 规模单次前向毫秒级，不预缓存 user 向量）；模型权重保持离线训练，不做参数在线更新——这是 Kafka/Flink 流式特征 + Monolith 在线训练的诚实单机替身，演示话术注明工业对应物（D8）；
  3. **即时生效路径**：ItemCF 种子集合（最近交互优先）、已看过滤、精排序列特征与类型偏好交叉特征均从同一状态层读取——点击后下一次推荐请求全部反映新行为。
- 负反馈（"不感兴趣"按钮）同样回流：加入已看/抑制集合，并在 ItemCF 种子中降权。
- 时延核算：user tower 前向 + SASRec 编码 + ANN 检索 + 200 候选精排，CPU 上合计远低于 A4 的 500ms 目标。

## 5. 服务与前端

- **FastAPI**：`/api/recommend?user_id=&mode=full|popular&rows=` 返回行式 JSON（`mode` 即消融开关）；`/api/event` 接收点击/负反馈回流（O1：更新用户状态实时层，下次请求生效）；`/api/user` 切换用户画像；`/api/query` 自然语言查询（M5）。
- **前端**：无构建工具链的静态页（原生 JS 或 CDN 引入 Vue），Netflix 风格多行布局 + TMDB 海报横向滚动 + 理由气泡。
- **消融演示模式（O3：默认开启）**：界面常驻开关切换「纯热门 vs 完整链路」（默认完整链路），支持同屏对比布局（上：热门基线 / 下：个性化），并实时展示两侧列表的多样性/长尾占比差异——这是最有效的"效果证明"交互，与评测体系（§6 基线对比）互为印证。

## 6. 评测体系（演示的数据支撑）

| 层 | 指标 | 说明 |
|---|---|---|
| 准确性 | Recall@10/20、NDCG@10、HR@10 | 时间切分，杜绝泄漏（文档 02_06 §9 第五层） |
| 各阶段 | 单召回通道 vs 融合召回 vs +粗排 vs +精排 的漏斗逐级指标 | 演示漏斗各层的增量价值 |
| Beyond-accuracy | 列表内多样性（ILAD）、目录覆盖率、长尾占比、流行度偏差 | 文档 01 §5.4：多样性是业务需求 |
| 基线对比 | **调好参的热门推荐**（非个性化基线） | Ferrari Dacrema 教训：必须打赢简单强基线，否则"进步"不可信（文档 01 §5.2）；与 O3 消融开关同源，线上线下一致 |

产出一份可展示的评测对比页/表，作为评审演示的"效果证明"环节。

## 8. 构建里程碑（"快速"的落地路径）

| 里程碑 | 内容 | 产出 |
|---|---|---|
| **M1（第 1 天）** | 数据管线 + ItemCF + 热门召回 + 规则重排 + FastAPI + 极简页面 | **端到端可演示的最小系统** |
| M2（第 2 天） | 双塔训练 + Faiss、SASRec-lite，替换进召回层 | 多路召回成型 |
| M3（第 3 天） | DeepFM-lite 精排 + MMR 重排 + 评测报告 | 漏斗完整 + 效果数据 |
| M4（第 4 天） | Web 界面完善（多行/海报/理由/用户切换）+ 实时回流（用户状态层 + 在线前向，O1）+ LLM 层 + 消融开关（O3） | 演示完成态 |
| M5（第 5 天，可选） | 自然语言查询、同屏对比视图、评测展示页、演示脚本 | 演示加分项 |

关键原则：**M1 结束即有完整可跑系统**，此后每个里程碑都是接口内的替换增强。若中途受挫，任意里程碑处截断均可交付。

## 9. 关键决策与备选方案

| # | 决策 | 备选 | 取舍理由 |
|---|---|---|---|
| D1 | ML-1M 数据集 | ML-25M/32M | 演示优先、CPU 分钟级训练、评审环境零依赖；代价：ANN 规模价值体现不出（3700 部暴力检索亦可）。缓解：检索走 Faiss 接口抽象，文档注明 25M 时换 HNSW |
| D2 | 保留极简粗排 | 砍掉粗排 | Demo 规模下粗排无实际收益，但四段完整性对评审讲解有价值；诚实标注其"架构位"属性 |
| D3 | 单目标精排 + 多目标接口预留 | 伪造/模拟多目标标签 | 不造假；演示话术将"多行为标签缺失"作为公开数据已知空白讲清（加分而非减分） |
| D4 | LLM 异步解耦 + 缓存（延迟优化）+ 降级 | LLM 进主链路 | O2 预算无上限：放开的是调用范围（含 NL 查询），不变的是可用性设计——评审现场零风险；符合"LLM 与传统链路互补"的研究结论 |
| D5 | SQLite 单文件存储 | Redis/MySQL/特征平台 | 演示规模不需要；文档标注工业对应物 |
| D6 | SASRec 做序列召回 | BERT4Rec / GRU4Rec | 自回归目标与线上 next-item 一致；GRU4Rec 长序列弱；BERT4Rec 有训练-推理目标偏差（文档 02_01 §4） |
| D7 | 评分 ≥4 = 正反馈，时间切分 | 随机切分 / 全量评分回归 | 文档 01 §5.2 明确的时间泄漏与离线-在线错位风险，从源头规避 |
| D8 | 实时回流 = 在线更新输入状态（序列/画像/已看），模型参数离线训练 | 在线训练/参数热更新（Monolith 式） | O1"立即变化"用在线前向即可满足（毫秒级）；单机 Demo 无流式设施；工业对应物见文档 03 文档 1（Flink/Monolith），演示话术注明 |

## 10. 风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 离线指标好 ≠ 真实推荐效果（评分≠观看行为、无曝光日志，文档 01 §5.2） | 演示话术如实说明边界；beyond-accuracy 指标补位 |
| R2 | LLM 输出格式漂移/幻觉 | JSON mode + 候选集 ID 白名单校验 + 失败降级 |
| R3 | 冷启动用户演示体验差 | 演示脚本预置高活跃真实用户 ID；新用户走热门 + LLM 询问偏好 |
| R4 | 评审环境无外网（TMDB/LLM 均不可达） | 海报 URL 离线缓存；LLM 全链路可关；系统本地化运行 |
| R5 | 双塔/SASRec 调参超期 | M1 的 ItemCF 基线保底，漏斗照常演示，弱模型只是指标略低 |
| R6 | 时间预估失准 | 里程碑串行交付，任意截断可演示（§8） |
| R7 | 实时状态层进程重启丢失演示期行为 | 写透 SQLite；启动时从 `events` 表重建内存态；演示前预热 |
