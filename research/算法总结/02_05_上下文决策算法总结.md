# 长视频推荐中的上下文决策算法详解

你选中的内容其实是“上下文感知推荐”里的几类方法。它们的目标不是单独提高离线 AUC，而是让推荐结果**更符合用户当前所处的场景**：时间、设备、观看进度、家庭、页面、实时行为等。

下面逐项介绍。

---

## 1. 时间上下文：时间特征 + 用户历史模式

### 解决什么问题

同一个用户在不同时间的偏好不同。

例如：

- 周末白天：家庭片、综艺、轻喜剧；
- 深夜：惊悚、悬疑、犯罪、成人向内容；
- 工作日通勤：短综艺、单集纪录片；
- 节假日：系列电影、合家欢内容；
- 用户刚看完一集剧：优先推荐下一集。

### 输入特征

常见时间特征包括：

- 小时；
- 星期几；
- 是否周末；
- 是否节假日；
- 季节；
- 用户当前会话开始时间；
- 用户历史观看时间分布；
- 影片上线时间；
- 剧集更新时间。

### 常用建模方法

#### 1. 时间特征拼接

最简单的方法是把时间特征直接加入排序模型：

```text
用户特征 + 影片特征 + 时间特征 → DNN / FM / DeepFM / DIN → 排序分数
```

例如：

- user embedding；
- item embedding；
- hour embedding；
- weekday embedding；
- is_weekend；
- holiday type。

优点是实现简单，适合作为基础版本。

缺点是模型只能学到比较粗的时间偏好。

#### 2. 周期编码

时间具有周期性，例如 0 点和 23 点其实比较接近，不适合只用普通数字表示。

常用方法是 sin/cos 编码：

```text
hour_sin = sin(2π × hour / 24)
hour_cos = cos(2π × hour / 24)
weekday_sin = sin(2π × weekday / 7)
weekday_cos = cos(2π × weekday / 7)
```

这样可以表达“深夜相邻”“周末相似”等周期关系。

#### 3. 用户时间偏好模型

为每个用户学习不同时间段的偏好分布，例如：

```text
用户 u 在周末白天喜欢：家庭片、动画、综艺
用户 u 在深夜喜欢：悬疑、犯罪、惊悚
```

可以用以下方式实现：

- 用户 × 时间段 embedding；
- context-aware matrix factorization；
- 时间条件化的双塔模型；
- DIN / Transformer 中加入时间注意力。

#### 4. Context-aware Tensor Factorization

把推荐建模为：

```text
用户 × 影片 × 上下文 → 评分 / 点击 / 播放概率
```

上下文可以是：

- 时间段；
- 设备；
- 地理位置；
- 是否节假日。

模型会学习类似：

```text
score(user, item, context)
```

这类方法比只用用户-影片二阶关系更适合上下文敏感场景。

### 长视频应用示例

系统发现用户 A 在周末白天经常和孩子一起看动画，在工作日深夜经常看悬疑剧。那么：

- 周末白天：提高动画、合家欢电影、综艺的权重；
- 深夜：提高悬疑、犯罪、惊悚、剧情向内容的权重。

### 优点

- 实现成本较低；
- 能显著提升推荐的场景适配性；
- 适合工业系统的排序模型。

### 局限

- 时间特征容易和家庭成员、设备混淆；
- 用户行为日志可能被推荐系统本身的历史偏差污染；
- 长视频观看决策通常滞后于时间点，例如用户晚上收藏、第二天晚上才观看。

## 2. 设备上下文：Device embedding + 场景模型

### 解决什么问题

同一个用户在不同设备上的观看行为可能完全不同。

例如：

- 手机：短视频、预告片、单集综艺、轻内容；
- 电视：电影、连续剧、长纪录片；
- 平板：家庭动画、旅行纪录片；
- 投屏：家庭电影、聚会内容。

### 输入特征

常见设备特征包括：

- 设备类型；
- 操作系统；
- 屏幕尺寸；
- 是否电视；
- 是否移动端；
- 是否支持 4K / HDR；
- 登录方式；
- 网络类型；
- 设备使用时间。

### 常用建模方法

#### 1. Device embedding

把设备类型映射成一个向量：

```text
手机 → [0.2, -0.4, 0.8, ...]
电视 → [0.9, 0.1, -0.3, ...]
```

然后与用户、影片 embedding 一起输入排序模型。

这种方法的优点是简单、通用。

#### 2. 用户 × 设备交叉特征

只使用全局 device embedding 不够，因为不同用户在不同设备上的偏好不同。

可以加入交叉特征：

```text
user × device
item × device
user × item × device
```

例如：

```text
用户 A 在电视上喜欢纪录片
用户 A 在手机上喜欢短综艺
```

#### 3. 场景模型

设备不仅是硬件，也代表场景。

例如：

```text
电视 = 客厅场景 = 可能多人观看、观看时间较长
手机 = 个人场景 = 可能碎片化时间、短内容
投屏 = 聚会或家庭场景
```

因此可以构建一个“场景向量”：

- personal / family / co-viewing；
- long session / short session；
- lean-back / active browsing；
- daytime / nighttime；
- high-bandwidth / low-bandwidth。

### 长视频应用示例

用户 B：

- 手机上经常看 20 分钟以内内容；
- 电视上经常看 2 小时电影或连续剧。

系统可以在手机端降低长电影权重，在电视端提高电影和剧集权重。

### 优点

- 设备信号稳定、容易获取；
- 对智能电视和移动端差异明显的平台很有价值；
- 能提升页面和内容格式适配。

### 局限

- 设备和家庭成员强相关，容易混淆；
- 多设备续看会让单设备行为不完整；
- 过度依赖设备可能导致推荐刻板化，例如“手机永远不推长电影”。

## 3. 观看进度：Sequential State Model

### 解决什么问题

长视频尤其是电视剧有明显的观看进度。

用户可能处于：

- 还没开始看；
- 看完第一集；
- 看到第三季第五集；
- 中途弃剧；
- 刚看完一季；
- 等待每周更新；
- 反复重看某些集。

如果推荐系统只把“剧”当成一个 item，就会丢失这些状态。

### 输入特征

常见进度特征包括：

- 是否看过该剧；
- 已看集数；
- 当前集数；
- 已看季数；
- 距离上次观看时间；
- 上次观看完成度；
- 是否弃剧；
- 是否等待更新；
- 是否收藏但未看；
- 观看速度；
- 连续观看天数。

### 常用建模方法

#### 1. 显式进度状态机

用规则先判断用户状态：

```text
未观看
刚开始
追剧中
暂停中
弃剧风险
等待更新
已完结
重看中
```

不同状态使用不同推荐策略。

例如：

```text
追剧中 → 优先推荐下一集
弃剧风险 → 推荐更强钩子的剧集或降低推荐强度
等待更新 → 推荐相似剧或花絮
已完结 → 推荐同 IP 或相似题材
```

优点是可解释、可控、容易上线。

#### 2. 序列模型：RNN / LSTM / GRU

把用户历史观看序列输入循环网络：

```text
看过的节目序列 → RNN → 用户当前状态
```

模型可以学习：

- 用户当前正在追什么；
- 兴趣是否正在变化；
- 是否可能继续看下一集；
- 是否可能弃剧。

#### 3. Self-attention / Transformer

例如 SASRec、BERT4Rec。

它们的核心思想是：不是把历史观看行为平均处理，而是根据当前候选内容动态关注历史中最相关的行为。

例如当前候选是悬疑剧，模型可能重点关注用户之前看过的悬疑剧，而不是动画或综艺。

#### 4. 下一集预测模型

专门预测：

```text
P(user watches next episode | current progress, time, device, history)
```

目标可以是：

- 继续观看下一集；
- 当天继续观看；
- 本周继续观看；
- 完成本季；
- 弃剧概率。

#### 5. 生存模型 / 流失模型

用于估计用户继续观看或流失的概率。

例如：

```text
P(用户还会继续看这部剧 | 已看集数、停留时长、暂停行为)
```

适合优化长期留存。

### 长视频应用示例

用户 C 正在看一部剧的第 4 季第 6 集，昨天刚看完一集。系统不应该把它当成普通候选，而应该把“继续看第 7 集”放在首页显著位置。

如果用户 D 已经两周没有继续看某剧，系统可以判断其弃剧风险较高，此时：

- 降低继续推送该剧的强度；
- 推荐更容易重新唤起兴趣的短内容；
- 推荐同题材但节奏更快的内容。

### 优点

- 对电视剧推荐特别重要；
- 能显著提升续看体验；
- 可以直接服务于长期留存。

### 局限

- 需要较细粒度的观看日志；
- 多设备、多账户会污染状态；
- 状态定义复杂，尤其是“弃剧”和“暂时不看”难以区分。

## 4. 家庭上下文：Household Model + Group Recommendation

### 解决什么问题

智能电视和流媒体账户经常不是个人账户，而是家庭账户。

例如：

- 一个账户里有爸爸、妈妈、孩子；
- 电视上有多个 profile；
- 用户忘记切换 profile；
- 多人共同观看；
- 一部历史剧是爸爸看的，动画是孩子看的。

如果系统只学一个“账户画像”，容易得到混乱偏好。

### 输入特征

家庭上下文可能包括：

- 账户内多个 profile；
- 观看时间；
- 设备；
- 内容类型；
- 年龄分级；
- 儿童模式；
- 家庭成员切换记录；
- 共同观看历史；
- 收藏列表；
- 观看完成度。

### 常用建模方法

#### 1. 账户画像拆分

目标是从混合账户中识别不同用户模式。

例如一个账户的历史里同时存在：

- 儿童动画；
- 体育比赛；
- 悬疑剧；
- 爱情电影；
- 纪录片。

可以用聚类方法拆分：

```text
账户历史 → 行为聚类 → 疑似用户画像 1、2、3
```

常用算法：

- K-means；
- Gaussian Mixture Model；
- topic model；
- session clustering。

#### 2. Profile-aware Recommendation

如果用户已经使用独立 profile，系统可以直接学习：

```text
profile_id embedding
user preference
family context
```

难点在于：

- 用户可能不切换 profile；
- 儿童误用成人 profile；
- 共看行为仍会混合画像。

#### 3. Household Model

在个人画像之外，再学习家庭整体偏好：

```text
个人画像：用户 A 喜欢惊悚
家庭画像：这个家庭周末常看合家欢动画
```

推荐时可以同时考虑：

```text
个人偏好 + 家庭偏好 + 当前场景
```

例如：

- 个人手机推荐：更偏向个人偏好；
- 电视推荐：更偏向家庭偏好。

#### 4. Group Recommendation

当多个用户共同观看时，需要推荐“大家都能接受”的内容。

常见策略有：

**1. 平均策略**

```text
推荐分数 = 多个成员偏好分数的平均值
```

优点：简单。

缺点：可能推荐谁都不讨厌、但谁都不喜欢的内容。

**2. 最大满意度策略**

优先让最不容易被满足的成员满意：

```text
maximize min(member satisfaction)
```

适合家庭中需要照顾孩子或长辈的场景。

**3. 加权策略**

根据影响力加权，例如：

```text
主账号用户权重更高
儿童内容安全性权重更高
当前遥控器使用者权重更高
```

**4. 公平性策略**

保证推荐结果中不同成员的偏好都有一定体现。

例如首页同时包含：

- 一部合家欢电影；
- 一部悬疑剧；
- 一部动画。

### 长视频应用示例

周末晚上，电视端识别到可能是家庭共看场景。系统推荐：

- 合家欢动画；
-冒险电影；
- 轻喜剧；
- 纪录片。

而不是只根据某个人深夜的惊悚片偏好继续推荐惊悚内容。

### 优点

- 更符合智能电视真实使用场景；
- 有助于提升家庭订阅价值；
- 可以降低账户混合画像带来的推荐误差。

### 局限

- 家庭成员识别困难；
- 涉及隐私和合规；
- 共看行为识别依赖行为模式，而非真实身份；
- 儿童安全约束必须优先于推荐效果。

## 5. 共看场景：Co-viewing Detection + Group RecSys

### 解决什么问题

共看场景是家庭推荐的更细分问题。

典型场景：

- 情侣一起看爱情片或悬疑剧；
- 父母和孩子一起看动画；
- 朋友聚会看电影；
- 多人一起看综艺或比赛。

### 共看信号

可以从以下行为推断：

- 同一时间段内多个 profile 被访问；
- 快速切换 profile；
- 观看内容跨越多个成员偏好；
- 暂停、回放、跳过行为；
- 儿童内容在成人时段被观看；
- 深夜出现不适合单人偏好的内容类型；
- 多次搜索“适合两个人看的电影”。

### 常用建模方法

#### 1. 规则识别

例如：

```text
如果周末晚上 + 电视端 + 内容评级为家庭向 + 混合历史偏好
则标记为疑似家庭共看
```

优点是可控、安全。

缺点是召回率低，容易漏掉很多场景。

#### 2. 会话聚类

把连续观看行为聚类为 session，再判断一个 session 的内容分布是否属于多个用户偏好。

例如：

```text
Session A：动画 + 综艺 + 家庭电影 → 可能亲子共看
Session B：悬疑剧 + 爱情电影 → 可能情侣共看
```

#### 3. 概率混合模型

假设一个观看会话由多个潜在用户共同产生：

```text
Session 观看行为 = 用户 A 偏好 × 权重
                 + 用户 B 偏好 × 权重
                 + 家庭共同偏好 × 权重
```

可以使用：

- mixture model；
- latent topic model；
- hierarchical Bayesian model；
- sequence model with mixture weights。

#### 4. Group RecSys

在识别出共看成员后，再进行群组推荐。

核心问题从：

```text
给一个用户推荐什么
```

变成：

```text
给一组用户推荐什么
```

常用目标包括：

- 平均满意度；
- 最小满意度；
- 公平性；
- 多样性；
- 安全性。

### 长视频应用示例

系统识别到电视端周六晚上可能是亲子共看场景，于是推荐：

- 合家欢动画电影；
- 儿童纪录片；
- 轻冒险剧；
- 低惊吓等级的奇幻内容。

同时避免推荐：

- 暴力犯罪剧；
- 成人向惊悚片；
- 复杂政治剧。

### 优点

- 明显提升电视场景推荐体验；
- 有助于家庭留存；
- 能提高推荐的安全性。

### 局限

- 共看识别本质上很难，容易误判；
- 不应过度推断家庭成员身份，有隐私风险；
- 共看偏好可能和单人偏好混杂；
- 儿童安全规则必须优先于个性化。

## 6. 页面上下文：Page-aware Ranking

### 解决什么问题

同一个影片在不同页面、不同位置的作用不同。

例如：

- 首页：需要多样化、有吸引力；
- 搜索页：相关性优先；
- 详情页：推荐相关影片或同系列内容；
- 完结页：优先推荐下一集或相似剧；
- 榜单页：强调权威感和热门度；
- 搜索无结果页：需要探索和兜底推荐。

如果所有页面都用同一个排序公式，效果会很差。

### 输入特征

页面上下文包括：

- 页面类型；
- 页面位置；
- 当前页面已有内容；
- 用户入口来源；
- 搜索词；
- 当前影片详情；
- 是否详情页；
- 是否播放完毕页；
- 页面目标：探索、续看、转化、发现；
- 屏幕位置：首屏、第二屏、横向列表。

### 常用建模方法

#### 1. Page-type Model

为不同页面训练不同模型：

```text
首页模型：优化点击、播放、多样性
搜索模型：优化相关性
详情页模型：优化相关内容
完结页模型：优化续看
榜单模型：优化可信度和点击
```

优点是目标清晰。

缺点是模型多、维护成本高。

#### 2. Page embedding

将页面类型和页面位置编码为 embedding，输入统一模型：

```text
user + item + page embedding + position embedding → score
```

这样模型可以学到：

```text
同一部影片在首页、搜索页、详情页的点击概率不同
```

#### 3. Position Bias Modeling

推荐位置本身会影响点击率。用户更容易点击首屏内容，因此不能简单认为首屏点击率高是因为内容更好。

常用方法：

- position as feature；
- inverse propensity weighting；
- counterfactual learning；
- position-aware ranking。

目标是从数据中区分：

```text
内容本身好
```

和

```text
只是位置好
```

#### 4. Listwise Ranking

普通排序模型只看单个 item，而 listwise ranking 优化整个列表。

典型方法：

- LambdaMART；
- listwise neural ranking；
- transformer-based list ranking。

输入：

```text
候选列表 + 用户特征 + 页面上下文
```

输出：

```text
整个列表的排序
```

适合首页这种强调整体体验的场景。

#### 5. Page-aware Diversity

首页不只是排序，还要考虑列表组合。

例如不能连续推荐：

```text
悬疑剧 1、悬疑剧 2、悬疑剧 3、悬疑剧 4
```

可以加入多样性目标：

- 类型多样；
- IP 多样；
- 长度多样；
- 情绪多样；
- 新旧内容混合；
- 商业内容与个性化内容混合。

### 长视频应用示例

用户刚看完一部电影：

- 完结页第一优先级：继续看同系列下一部；
- 第二优先级：相似题材电影；
- 第三优先级：用户收藏但未看的内容；
- 不应该优先推荐完全无关的新剧。

用户在搜索“科幻”：

- 搜索页优先相关性；
- 可以加入少量探索性科幻内容；
- 但不应强行插入热门爱情片。

### 优点

- 贴近真实产品形态；
- 可以同时优化点击、多样性、页面体验；
- 适合工业部署。

### 局限

- 页面类型和位置会造成偏差；
- 多页面多模型会提高维护成本；
- 页面目标可能与全局长期目标冲突。

---

## 7. 实时行为：Online Learning + Streaming Update

### 解决什么问题

用户偏好会实时变化，尤其是长视频场景中：

- 刚看完一部悬疑片；
- 刚搜索某个演员；
- 刚收藏一部电影；
- 刚跳过多个动画；
- 刚连续看完三集；
- 刚对推荐点击“不感兴趣”。

如果模型只每天或每周更新，就无法及时响应。

### 输入信号

实时行为包括：

- 点击；
- 播放；
- 暂停；
- 快进；
- 回看；
- 跳过；
- 搜索；
- 收藏；
- 加入片单；
- 评分；
- 关闭推荐卡片；
- 点击“不感兴趣”；
- 观看时长；
- 完播率。

### 常用建模方法

#### 1. 实时特征更新

模型本身不更新，但输入特征实时变化。

例如：

```text
最近 1 小时搜索词
最近 3 部观看影片
当前 session 观看类型
最近点击但未播放的影片
最近负反馈类型
```

优点是延迟低、系统稳定。

缺点是模型参数无法适应新偏好。

#### 2. Online Learning

模型随着新数据持续更新。

常见形式：

- SGD / Adam 增量更新；
- FTRL；
- Online Logistic Regression；
- Online Matrix Factorization。

适合处理高频实时信号。

#### 3. Streaming Learning

数据以流的形式进入系统：

```text
用户行为日志 → 流处理 → 特征更新 → 模型更新
```

常见组件：

- Kafka；
- Flink；
- Spark Streaming；
- feature store；
- real-time model server。

#### 4. Near-line Learning

介于离线和在线之间：

- 实时收集行为；
- 快速生成新特征；
- 分钟级或小时级更新模型。

工业系统常用 near-line，因为完全实时更新风险较高。

### 长视频应用示例

用户刚看完一部恐怖片，并马上搜索“心理惊悚”。

系统可以实时更新当前 session 的偏好权重：

- 提高心理惊悚、悬疑、犯罪题材权重；
- 降低喜剧和综艺权重；
- 优先推荐用户可能想连续观看的同类影片。

但也要避免过度反应：用户看完一部恐怖片不代表长期偏好已经改变。

### 优点

- 能捕捉短期兴趣；
- 提升连续观看体验；
- 对新片和新剧上线初期的反馈很敏感。

### 局限

- 容易被短期噪声误导；
- 实时系统复杂，稳定性要求高；
- 在线更新可能带来安全风险；
- 需要防止负反馈被过度放大。

---

## 8. 探索与利用：ε-Greedy、UCB、Thompson Sampling、Contextual Bandit

### 解决什么问题

推荐系统面临一个基本矛盾：

- **利用 exploitation**：推荐已知用户喜欢的内容；
- **探索 exploration**：尝试用户可能喜欢但尚未观察的内容。

如果只利用，系统会陷入旧偏好；如果只探索，用户体验会变差。

---

## 8.1 ε-Greedy

### 核心思想

以大概率选择当前最优内容，以小概率随机探索。

公式：

```text
以 1 - ε 的概率选择当前分数最高的内容
以 ε 的概率随机选择一个其他内容
```

例如：

```text
ε = 0.05
```

表示 95% 的情况推荐当前最优内容，5% 的情况尝试新内容。

### 优点

- 极其简单；
- 容易实现；
- 适合作为 baseline。

### 缺点

- 探索是随机的，不聪明；
- ε 固定不灵活；
- 可能探索明显不适合的内容；
- 对长视频来说成本高，因为推荐错一部电影的代价很大。

---

## 8.2 UCB：Upper Confidence Bound

### 核心思想

不只看内容的平均表现，还看不确定性。

公式可理解为：

```text
UCB分数 = 估计收益 + 探索奖励
```

探索奖励通常与尝试次数有关：

- 尝试次数少 → 不确定性高 → 探索奖励大；
- 尝试次数多 → 不确定性低 → 探索奖励小。

一个新电影虽然暂时没有高点击率，但如果曝光很少，系统可能会尝试给它更多机会。

### 优点

- 比随机探索更聪明；
- 能给新内容公平尝试机会；
- 适合新片冷启动。

### 缺点

- 需要较准确的方差估计；
- 如果奖励信号噪声大，容易误判；
- 长视频的反馈周期较长，不像短视频能快速观察到结果。

---

## 8.3 Thompson Sampling

### 核心思想

为每个内容维护一个奖励分布，而不是单一分数。

每次推荐时：

1. 从每个内容的后验分布中采样一个分数；
2. 选择采样分数最高的内容。

例如：

- 电影 A：历史表现很好，分布集中在高分区；
- 电影 B：新片，分布很宽，既可能很好也可能很差。

Thompson Sampling 会自然地在“确定好内容”和“不确定但可能好的内容”之间平衡。

### 优点

- 探索策略比 ε-Greedy 更自然；
- 在很多场景中效果好于 UCB；
- 适合批量推荐和多臂选择。

### 缺点

- 实现比 ε-Greedy 复杂；
- 需要维护后验分布；
- 对奖励定义非常敏感。

---

## 8.4 Contextual Bandit

### 核心思想

普通 Bandit 只根据内容历史表现选择，而 Contextual Bandit 会结合上下文。

输入：

```text
用户特征 + 内容特征 + 场景特征
```

输出：

```text
选择哪个内容能带来最大期望收益
```

例如：

```text
深夜 + 电视 + 成人用户 + 悬疑偏好
```

系统选择的内容会不同于：

```text
周末白天 + 家庭电视 + 亲子场景
```

### 常见算法

- LinUCB；
- Logistic Bandit；
- Neural Contextual Bandit；
- Thompson Contextual Bandit。

### 长视频应用示例

Netflix 的个性化封面选择就是典型的 contextual bandit 思路：

- 同一部电影准备多个海报；
- 根据用户和上下文选择最可能被点击的海报；
- 根据反馈持续更新选择策略。

### 优点

- 能结合用户、影片和场景；
- 适合实时个性化决策；
- 比全量强化学习更容易上线。

### 缺点

- 只优化短期反馈，长期价值建模较弱；
- 奖励函数设计很关键；
- 容易强化点击率而不提升满意度。

---

## 9. 强化学习：MAB、DQN、Policy Gradient

### 解决什么问题

传统监督学习优化的是单次预测：

```text
预测用户会不会点击
```

强化学习优化的是长期累积收益：

```text
这次推荐是否会让用户继续看、订阅、留存、长期满意
```

### 核心概念

强化学习包含：

- **State**：用户当前状态，例如观看历史、设备、时间、进度；
- **Action**：推荐什么内容、展示什么封面、放在什么页面位置；
- **Reward**：点击、播放、完播、续看、订阅、留存、满意度；
- **Policy**：推荐策略；
- **Value**：长期收益估计。

目标：

```text
选择能够最大化长期累积 reward 的 action
```

---

## 9.1 MAB：Multi-Armed Bandit

MAB 是最简单的强化学习。

每个内容或策略可以看作一个老虎机。

系统在多个选项之间选择：

- 推荐热门片；
- 推荐新片；
- 推荐小众片；
- 推荐同类型片；
- 推荐探索性内容。

它适合短期探索与利用，但不建模复杂长期状态。

适合：

- 新片曝光；
- 封面选择；
- 推荐理由选择；
- 小规模策略选择。

---

## 9.2 DQN：Deep Q-Network

DQN 用神经网络估计每个动作的长期价值：

```text
Q(state, action) → expected future reward
```

例如：

```text
state = 用户观看历史 + 当前时间 + 设备 + 剧集进度
action = 推荐某部影片
reward = 播放、完播、续看、留存
```

DQN 适合动作空间可控的场景，例如：

- 是否推荐下一集；
- 是否推荐相似影片；
- 是否推荐新内容；
- 是否插入探索内容。

### 优点

- 能建模长期价值；
- 比简单 Bandit 更适合序列决策。

### 缺点

- 长视频动作空间巨大；
- reward 延迟严重；
- 训练不稳定；
- 离线日志存在偏差；
- 直接在线实验风险高。

---

## 9.3 Policy Gradient

Policy Gradient 不估计每个动作的价值，而是直接学习一个策略：

```text
π(action | state)
```

即给定用户状态，输出推荐内容的概率分布。

常见方法：

- REINFORCE；
- Actor-Critic；
- PPO；
- DDPG；
- A3C。

### 适合场景

- 大规模推荐；
- 连续动作空间；
- 序列推荐；
- 页面级策略优化；
- 长期留存优化。

### 优点

- 不需要枚举所有动作价值；
- 可以处理大规模候选；
- 适合策略优化。

### 缺点

- 样本效率低；
- 对 reward 设计敏感；
- 容易出现短期指标提升但长期体验下降；
- 需要离线评估和安全部署机制。

---

## 10. 各算法之间的关系

可以把这些方法放在同一个框架中理解：

```text
上下文感知推荐 =
    状态识别
  + 特征建模
  + 策略选择
  + 实时反馈更新
  + 长期价值优化
```

对应关系是：

| 任务 | 对应算法 |
|---|---|
| 判断当前时间偏好 | 时间特征、周期编码、context-aware model |
| 判断当前设备场景 | device embedding、场景模型 |
| 判断用户追剧状态 | sequential state model、RNN、Transformer |
| 识别家庭或共看 | clustering、household model、group recommendation |
| 适配不同页面 | page embedding、listwise ranking、position bias model |
| 响应实时行为 | online learning、streaming update |
| 平衡探索与利用 | ε-Greedy、UCB、Thompson Sampling、Contextual Bandit |
| 优化长期收益 | MAB、DQN、Policy Gradient |

---

## 11. 长视频场景下的实践建议

### 1. 先做上下文特征，再上复杂模型

工业上最稳妥的顺序是：

1. 时间、设备、页面特征；
2. 用户 × 上下文交叉特征；
3. 观看进度状态；
4. 家庭和共看识别；
5. Contextual Bandit；
6. 强化学习。

### 2. 不要把短期信号当成稳定偏好

用户刚看完一部惊悚片，不代表长期只喜欢惊悚片。应该区分：

- 当前 session 偏好；
- 近期偏好；
- 长期画像；
- 家庭偏好；
- 上下文条件偏好。

### 3. 推荐目标必须和长期价值对齐

如果只优化点击，系统可能学到标题党。长视频更适合关注：

- 完播率；
- 续看率；
- 弃剧率；
- 用户满意度；
- 长期留存；
- 多样性；
- 内容探索。

### 4. 家庭和儿童场景要优先安全约束

在家庭或共看场景中，安全性应优先于个性化效果：

- 年龄分级；
- 儿童模式；
- 内容过滤；
- 隐私保护；
- 避免过度推断家庭成员身份。

---

## 一句话总结

> **时间、设备、观看进度、家庭、页面和实时行为解决“当前状态是什么”；Contextual Bandit 和强化学习解决“在这个状态下应该采取什么推荐动作”；Online Learning 解决“动作之后如何快速修正策略”。**
